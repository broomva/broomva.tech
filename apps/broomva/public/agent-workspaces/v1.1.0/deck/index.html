Field guide · Agentic engineering

The workspace
is the product.

Models are rented. Harnesses are swappable. What compounds is the place they work in: its instructions, memory, procedures, structure, and the colleagues beside them.

Seven acts · about forty-five minutes · press → to begin, G for the guide

Open. Everyone here has watched a strong model do weak work because it started cold: no context, no rules, no memory of yesterday. This talk is about the thing around the model.

Thesis: models get swapped every few months and harnesses keep converging. The workspace is the one asset that compounds, so design it as a product.

The thesis

Give the agent a filesystem and a shell.

A model guesses when it can't look. A workspace lets it look, run, and write down what it found.

Explicit. Every input is a file you can open, diff and cite.

Open. Bash runs whatever the harness allows: search, tests, scripts.

Durable. What it learns is written back, so the next run starts ahead.

Structure and philosophy decide how it works there. That is harness engineering.

Chat only: the agent answers from weights and the prompt. Claims it can't check drift off and dissolve: that's what hallucination looks like from the outside.

Filesystem + shell: the same agent reads files, runs commands, and writes notes back. Answers leave with citations. Most of the rest of the talk is about how to structure that filesystem so the agent's context gets better every session.

Act I

Workspaces

Where does the agent live?

A fine vine grows through a workspace window: the workspace as a living thing. Its real files settle where the branches end, and a cursor visits each one.

Act I covers a folder versus a workspace, six workspace layers, the sandbox-harness-wire split, filesystem medallion layers and an architecture-only review-system example. Read next: A folder is not a workspace.

I · Workspaces

A folder is not a workspace.

The difference is what survives the session.

Agent workspace

A working directory and a toolset for one agent on one task.

Useful. But context evaporates when the session ends, and the next agent starts cold.

Agentic workspace

A governed place that many agents work through.

Instructions, policy, memory, skills and a record outlive every session, so each run leaves the place a little smarter.

Left state: one agent, one folder. Watch the counter: sessions go up, retained knowledge stays at zero. Every run re-derives the same context.

Right state (→): the same agents now dock into rings: primer, policy, skills, memory, record. Each session drops something into memory before it leaves. That accumulation is the whole game.

I · Workspaces

Six layers an agent reads before it writes.

Read top-down, write bottom-up. The primer routes; it does not dump everything into context. Policy is data that hooks and CI enforce. Skills and knowledge load on demand. The record says what is in flight right now. Only the bottom layer is where bytes actually change.

Hover a plate. The rule under each is the one-line discipline that keeps that layer honest.

I · Workspaces

Sandbox, harness, wire.

Three layers, three different answers. Buy the box, swap the brain, and don't bet on the wire yet.

Sandbox: isolated microVMs with a persistent volume are a commodity now. Buy them.

Harness: the agent loop. Click through the harnesses: the integration rail underneath (an MCP server plus a CLI) never moves. If you integrate through one harness's internals, you've married it.

Wire: how a human on a phone or a desktop talks to a remote agent. The agent-client protocol (ACP) is stdio-first; its remote transport is still a draft. Keep that layer thin and replaceable.

I · Workspaces

Medallion layers live in the filesystem.

Each workspace keeps its own bronze, silver and gold as plain folders. A shared ledger records what was decided.

bronze/ Inputs as received. Append-only, hashed, never edited.

silver/ Typed and validated. Every value cites its bronze source.

gold/ Decisions and definitions the organization trusts.

Files are the agent's working memory. The ledger is the organization's.

The agent works in files because files are what agents are best at: grep, diff, read, write. So the medallion layers live inside the workspace's own filesystem, in its sandbox, next to its own ontology.

What leaves the sandbox is the record: activities, approvals and gold definitions go to one shared ledger. Toggle to many workspaces: each is sovereign over its files, and all of them write to the same system of record.

I · Workspaces · worked example

A review system, built on the pattern.

Architecture only, no domain specifics. One sandbox per case with the medallion layers as folders. The harness agent runs the review skill: the skill is the workflow. One reader subagent per document turns untrusted text into typed claims with quotes. Code verifies every quote and judges; a claim that can't be verified stays claimed and can only push the outcome toward manual review.

The shared Postgres ledger, outside the sandbox, records activities, approvals and gold definitions for every workspace. Step through the four beats.

II · Context

How an agent's context is built.

Everything the model knows this turn is what reached the window. The workspace decides what reaches it.

Hover any layer of the window. Each one has a source on disk, a moment it loads, and a budget.

Less guessing is the product of more grounded layers, not of a bigger model.

Bare: the harness system prompt and your message. Everything else the model needs, it fills in. That hatched block is guessing.

Workspace: the primer loads at boot, the memory index, hook injections at session start and on every prompt, skill descriptions, then whatever the agent reads and runs. The unknown shrinks. Hover the layers: each names where it comes from.

II · Context

Hooks turn recall into a reflex.

PrimerAsks for it
SkillKnows how

Three levers, increasing in force. CLAUDE.md and AGENTS.md ask the agent to load the graph: that is reasoning-enforced, so it gets skipped. Skills package how. Hooks execute every time, without the model deciding.

Walk the session left to right. Real output from this workspace: the intake hook injects the matched lens, the knowledge-graph constraints and the auto-loaded entities into every prompt. The Stop hook writes the session to the bridge so the next one can find it.

At 1,430 entities the compiled catalog is about 260K tokens: it fits a 1M-token window, so the catalog routes and the model reads. Add vectors when vocabulary diverges or the catalog outgrows the window.

A query fans out to every retriever the agent can call through bash or tools, and the answers come back cited. Local first: ripgrep and the compiled front-matter index are exact and free, and graph hops add structure flat search can't. Embeddings earn their place when words diverge or the catalog outgrows the window. Live systems come through MCP or APIs.

The point: retrieval is a toolbox the agent composes, not one database you bolt on.

III · Second brain

Most second brains are write-only.

0.9%

of 565 agent sessions in the seven days to 2026-10-26 loaded the knowledge graph (5 sessions). Capture is easy. Recall is the product.

measured 2026-10-26 · session telemetry

The fix is routing, not volume

Put recall on the startup path.

The primer routes to it. An intake hook surfaces matching entities. /kg load runs before planning. And when reads lag, prune production. Don't add more writers.

This number is from our own telemetry this week. Sessions write constantly: bookkeeping, ingestion, hooks. Almost none read. A graph nobody loads is a cost centre.

Toggle: the fix is putting recall where the agent already looks, at intake. The counter-intuitive part is the corrective action. When reads lag, you slow writes down.

III · Second brain

The loop that makes knowledge readable.

Memory holds facts about the owner. The graph holds claims about the world. The ledger holds what is in flight.

Walk the loop with →. Capture verifies sources at the door. Scoring keeps low-signal material as candidates. Links are explicit and linted. The index is one compiled catalog an agent can load cheaply. Load happens at intake with synonyms, and it reports what it missed. Then outputs cite entities, and new findings come back in.

The footnote matters: three stores, three jobs. Don't put owner preferences in the graph or world claims in memory.

III · Second brain

Insight hardens into mechanism.

Promote on the third instance, with a concrete mechanism, an invariant and a failure mode. Name what the new rule retires.

This is how the agent gives back to the graph. Most observations stay observations. When something recurs it becomes a memory fact or a scored entity. When a procedure recurs it becomes a skill with evals. When a rule must never be broken it becomes a hook, a policy gate or a test.

Each step up trades flexibility for force: prose persuades, executables enforce. The ratchet only turns on evidence, and every promotion names what it retires so the system doesn't just grow.

IV · Skills

A skill is a procedure,
not a prompt.

skills/knowledge/kg/ ├─ SKILL.md description is the router ├─ scripts/ deterministic core └─ evals/ routing + behavior tests --- name: kg description: Load graph context for a topic… USE WHEN … NOT FOR … ---

A skill is a folder: a SKILL.md, a deterministic script core, references, and evals. The description in the frontmatter is the only part that is always in context, so it is the router. Write it like a trigger spec: use when, not for.

The animation is progressive disclosure: a request scans the descriptions, one matches, its body loads, and references load only if needed.

IV · Skills

Skill, CLI, MCP.

One knows. One does. One reaches.

Repeatable judgment and stepsSkill
Deterministic, local, testable workCLI
Remote system, auth, shared across harnessesMCP server
A one-offJust ask

A skill that drives a small CLI beats a wide MCP surface: fewer tools in context, and a core you can test.

The most common design mistake is reaching for MCP by default. MCP earns its place for remote systems that need auth and should be shared across harnesses. Local deterministic work belongs in a CLI you can test. The skill is the knowledge of when and how to call either.

IV · Skills

Then the measured surprise (→). With 457 skills installed, the harness kept full descriptions for 26. The rest were bare names, and a bare name cannot trigger itself. More skills made each one less likely to fire. That's why the roster is rationed.

V · Structure

One place, many repos.

Governance is shared: one repo holds the primer, policy, lenses, skills, graph and record. Products are sovereign: 66 product repos under apps/, core/ and work/, each with its own history and release cadence. Worktrees are disposable: one per task, created from main, merged back through review, then swept.

V · Structure

One writer per tree.

Parallel agents never share a checkout. They share main, through review.

01Branch is the first action
02Reviewers read. They never write
03A live thread's worktree is the thread
04Unfinished work becomes a draft PR
05Janitor after merge, dry-run first

Each lane is an agent in its own worktree. Commits flow along the lane, hit review, and either merge with a flash or bounce back. Finished lanes fade: that's the janitor.

Every rule on the bottom row exists because we broke it once. Removing a live thread's worktree bricked the thread. Salvaging someone's uncommitted work silently lost provenance, which is why it now becomes a draft PR.

VI · Fleets

Roles, not agents.

Step through the roles. The owner sets intent and answers asks. A meta-orchestrator ticks on a schedule and only watches orchestrators and capacity. Orchestrators each own one initiative. Workers are bounded and isolated. Reviewers are never the writer: a different model where possible, at least a fresh context. Sensors observe and never act.

The “never” line under each role is the important half.

Four questions decide the mechanism. Independent work gets a fresh child in its own worktree, which also avoids anchoring it on your conclusion. Work that needs your context continues here.

The chart is why you shouldn't stretch one session forever: in a month of our transcripts, 158 of 838 sessions ran past 400K tokens and carried 87% of the cost. Long sessions roll over to a successor with a handoff doc.

VI · Fleets

Governance that scales with the fleet.

PaceFrom measured capacity, not hope
ReviewThe writer cannot certify its own work
PolicyExecutable gates. Prose is only advice
SensorsObserve and file. Agents act

Four principles, one pipeline, left to right. Pace: a governor sets lanes from measured headroom, several on green, one on amber, none on red, so work queues instead of failing mid-run. Review: an independent reviewer for substantive work, three strata for governance; rejections go back to the writer.

Policy: an executable gate before main. Sensors: they watch main and file tickets, and agents act on them. Governance scales because each of these is a mechanism, not a meeting.

VII · Leadership

The unit of work is now a loop.

When an attempt costs minutes, making gets abundant and deciding gets scarce.

Every question is something you can start today.

Every repeated task is something you can automate or improve.

Every piece of work leaves the system better: a note, a skill, a check.

The question moves from “can I do this?” to “should this exist, and how will I know it's right?”

Last act: what this asks of people. A task waits on someone deciding it's worth doing, then one attempt. A loop states intent, lets agents act in parallel, looks at what came back, sharpens the intent and runs again.

Watch the two gauges: the scarce resource moves from making to deciding. This is the premise of The New Dynamics of Agentic Leadership, the essay this act comes from.

VII · Leadership

Everyone leads a fleet.

What each person brings to their fleet is taste and judgment: knowing what good looks like, and deciding what to accept.

Delegation runs under a five-term contract, for agents and for people: intent, bounds, evidence, escalation, review. Step through the terms: each one adds a force to the same fleet and keeps acting after you move on. Intent turns wandering agents into a flow toward the goal. Bounds are a wall they bounce off, and the one heading for the red zone is stopped. Evidence streams receipts into your ledger. An escalation stops one agent until you answer. Review is a judge of a different colour before work lands on the gold line.

None of this is specific to code. Software got there first because tests made verification cheap.

VII · Leadership

Attention is the new ration.

Reversible drafts, research, branches: act and note it.

Costly long compute, many iterations: only inside a budget.

Irreversible or external spend, publish, merge outside policy, contact: a yes first, every time.

The measure of an autonomous system isn't how much it does without you. It's how precisely it calls you.

Forty threads that each want a look will eat a day. Classify every action: reversible work proceeds and is noted, costly work runs only inside a stated budget, and irreversible or external work waits for an explicit yes.

Toggle the gate: only a short ordered list reaches the human, each ask with context, options, a recommendation and a safe default. That is what the fleet governance in act six was for.

VII · Leadership

Goalposts teach waiting. Bars rise in the open.

People learn to wait when proposals get overridden, the leader decides anyway, the bar moves silently, or a failed attempt costs more than a passive miss.

Make everything queryable: decisions, standards and why they changed live in the same shared graph that people and agents read.

In agentic work the bar is supposed to move. The problem is who moves it and whether anyone can see it. First beat: the goalpost sits behind frosted glass that only the leader sees, and it moves after the team arrives, so the team stalls and waits. Second beat: the bar is written on a shared glass wall that people and agents query; each rise is logged with its reason, and the team keeps climbing.

That loops back to the second brain: the same queryable workspace that grounds agents also makes standards visible to people.

Epilogue

Better agents come from better harnesses.

Harness engineering is everything around the model, built layer by layer around the same orb: the loop, docked tools, the context shell, the guard rim that rejects what policy forbids, the scanning evals, and the gold workspace lattice that keeps what every layer deposits. Models will keep changing, and so will harness products. Harness engineering, everything around the model, is where work compounds; the workspace is its outermost ring.
